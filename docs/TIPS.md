## 1. 模型的运行环境

- `.pth` 只是权重。推理需要三样东西：
  - 权重；
  - PyTorch + `mjtf/model.py`，Windows、Mac、Linux 都有，CPU 推理每步几十毫秒；
  - **libriichi**：跟踪牌局状态、编码局面、判断合法动作、处理 mjai 协议。
- 平台限制只来自 libriichi：包里只有 Linux x86_64、Python 3.11 的 `.so`。它是 Rust + PyO3，可以在 Windows 上编译；补丁在 `final/.../code/libriichi_patched.diff`，基于 Mortal commit 见 `mortal_commit.txt`。在 Windows 上编译还没试过。
- 最省事的做法：在 Linux 或 WSL 上运行 `bot.py`，其他程序通过 mjai 协议（stdin/stdout，或包一层 HTTP）调用。
- 导出 ONNX 只能去掉对 PyTorch 的依赖，局面编码仍然需要 libriichi。

## 2. GRP 与 RL 奖励

- GRP（`grp_hanchan.pth`）训练得还可以：验证 CE 1.125，瞎猜为 1.386。没学会的是 SL 模型上的"最终顺位"辅助头（1.37），两者是不同的东西。
- GRP 按局奖励的噪声约为终局奖励的 1/10，学习更快；代价是 GRP 有偏差时奖励也会跟着偏。
- 推断（**未实测**）：换成终局奖励大概率不会更好。三次 RL 的成败由探索温度决定（temp 1 无效，0.5 有效），第 40 轮之后的退步更像对手池单一导致的过拟合。
- 对照实验的做法：`return_mode: "terminal"`，其余同 `records/rl_planA2.json`，跑 40 轮（约 3 h），再用 4 万局独立牌山对比。
- RL 想继续变强，优先改对手多样性，不要单纯延长训练。

## 3. 模型架构（`mjtf/model.py`，约 40M 参数）

- 34 种牌各为一个 token，加一个 CLS token。每个 token 的输入是该牌在 1014 个特征通道上的值。
  - 输入投影：Linear 1014→512 → GELU → Linear 512→512，加上可学习的牌身份嵌入。
- 12 层 Pre-LN Transformer 编码器：d512、8 头、FFN 2048、GELU、无 dropout。
- 输出头：
  - 牌 token → Linear(512→2)，给出 34 个打牌/杠牌分数和 3 个赤宝牌分数；
  - CLS → MLP，给出 9 个其他动作，合计 46 个动作，非法动作屏蔽；
  - CLS 上的辅助头：顺位(4)、本局点数变化(1)、价值(1)。
- 与 Mortal 的主要区别：Mortal 用 ResNet 卷积，这里用牌间注意力。
- SL 设置：
  - 损失 = 动作 CE + 0.2×点数变化 + 0.05×顺位 + 0.05×价值；
  - AdamW，lr 3e-4，warmup 3k，batch 1024，30 万步，bf16 + torch.compile；
  - 每局每家最多抽 64 个决策，加跨文件混洗缓冲。
- RL 设置：
  - PPO：clip 0.2，2 epoch，mb 1024，lr 1e-5，KL 系数 0.05（对 SL），熵 0.003；
  - 自对弈温度 0.5，每轮 500 seeds × 4 座位；
  - 对手一半是 SL，一半是历史版本。

## 4. 只输入"手牌 + 宝牌"能不能推理？

**能跑，但结果不可信。** 模型的 1014 个输入通道里，手牌和宝牌只占一小部分，其余主要是：

- 四家牌河：每张打出的牌、顺序（最近 6 张单独编码，按时间衰减加权）、手切还是摸切、立直宣言牌、是否宝牌；
- 四家副露；
- 立直状态（宣言、成立）；
- 点数、场风、局数、本场、供托、剩余牌数、可见宝牌计数；
- 自己的向听数、听牌和待牌；
- 当前可以执行的动作及对应的牌（吃、碰、和的对象）。

这些全部来自 `ref/Mortal/libriichi/src/state/obs_repr.rs`。只给手牌和宝牌时，其余通道全为 0，这种局面模型在训练中从未见过：防守、押引、读立直全部失效，可靠性无法保证。

**几种可行的做法：**

| 方案 | 做法 | 工作量 | 效果 |
|---|---|---|---|
| A. 实时喂事件（推荐） | 对局中按发生顺序把每个事件（摸、打、鸣、立直、新宝牌）转成 mjai JSON 喂给 `bot.py`，就是它现在的用法 | 小，只需写一个事件录入层 | 与训练完全一致 |
| B. 局面快照 → 合成事件 | 输入当前快照：自家手牌、四家牌河（含摸切/立直标记）、副露、宝牌、点数、场况，由程序按轮流顺序合成一段 mjai 事件，再交给 libriichi | 中，约 1 天 | 接近完整；鸣牌插入的先后可能有少量误差 |
| C. 纯 Python 重写编码器 | 把 obs_repr.rs 及状态跟踪（向听、待牌、安全牌等）移植到 Python，彻底去掉 libriichi | 大，数千行，且必须逐位一致 | 一致的话与 A 相同；有偏差就会悄悄变弱 |
| D. 只用手牌 + 宝牌 | 另训一个精简输入的"何切"模型 | 中到大，需要重新训练 | 只有牌效率，没有防守，明显弱于现有模型 |

无论哪种方案都需要"合法动作"信息（能不能吃、碰、立直、和），这部分原本也由 libriichi 计算。

**结论**：规则引擎做的不只是"规则"，它负责把整局历史整理成模型的输入，绕不开。真正要解决的是"怎么把真实对局的信息交给它"：边打边记录用方案 A，只有截图或局面描述用方案 B。
